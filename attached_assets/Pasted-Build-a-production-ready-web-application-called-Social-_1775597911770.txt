Build a production-ready web application called **Social Playout Manager** for deployment on our own Ubuntu servers, not on Replit.

## Goal

This system will let users:

* Upload video files and stream them to YouTube Live continuously like a FAST/live channel
* Create playlists and schedule playout
* Add closed captions support
* Accept inbound **RTMP** and **SRT** live feeds from outside contributors
* Give users their own ingest endpoints and stream keys
* Switch between file-based playout and live inputs
* Restream one source to multiple destinations at the same time, including YouTube and other social platforms
* Monitor stream health, errors, bitrate, and uptime

## Deployment model

This app is being built in Replit, but it will be deployed on our own infrastructure.

Target environment:

* Ubuntu 22.04 or 24.04
* Docker Compose for initial deployment
* PostgreSQL
* Redis
* Nginx reverse proxy
* FFmpeg workers running on our servers
* SRS or equivalent ingest server for RTMP/WebRTC if needed
* SRT ingest support
* Persistent shared storage for uploaded media
* Systemd or Docker for worker services

Do not assume Replit hosting limitations. Build this as a self-hosted production application.

## Required architecture

Split the system into two major layers:

### 1. Control Plane

Web application for:

* authentication
* user management
* channel creation
* asset upload and library
* playlist creation
* scheduling
* destination management
* ingest endpoint management
* monitoring dashboard
* admin controls
* logs and audit history

### 2. Media Plane

Worker-based media services for:

* FFmpeg playout
* RTMP ingest
* SRT ingest
* source switching
* multi-destination output
* fallback slate
* captions insertion/passthrough
* stream health monitoring
* automatic restart on failure

The control plane must manage the desired state in the database, and workers must pull jobs and report actual state back through APIs.

### Live Inputs

Each channel should be able to have one or more live inputs.

Support:

* RTMP ingest
* SRT ingest

For each live input generate:

* unique name
* channel assignment
* stream key/token
* ingest URL
* protocol type
* status
* last seen time
* bitrate and resolution if known

Examples:

* RTMP: `rtmp://ingest.yourdomain.com/live/{stream_key}`
* SRT listener mode with unique port or tokenized mapping

## Worker architecture

Create a worker service that can:

* fetch assigned jobs from the API
* start playout jobs
* stop playout jobs
* switch source between playlist/live input/fallback
* publish status back to control plane
* restart failed FFmpeg processes
* support multiple destinations per job

The worker should not require manual intervention for normal failures.

## Source modes

Support these operational modes:

### File-to-live

* Loop a file forever to YouTube or other destinations
* Or play a playlist continuously

### Live-to-live

* Receive RTMP or SRT ingest from a user
* Transcode/remux if needed
* Send to one or more destinations

### Hybrid channel

* Default to playlist playout
* Allow operator to cut to live input
* Return to playlist when live ends

### Fallback

* If live input fails, switch to slate or fallback asset
* If playlist is missing, use a default slate
